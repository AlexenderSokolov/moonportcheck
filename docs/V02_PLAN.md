# MoonPortCheck v0.2：完善交付检查流程，分 16 次提交到 GitHub

本文保存用户于 2026-09-26 明确要求实施的 v0.2 计划。计划身份为 `moonportcheck-v0.2-16-milestones`；如本文与用户原始消息不一致，以用户消息为准。本文是计划，不是功能完成或公开 CI 通过的证据；执行状态见 [V02_PROGRESS.md](V02_PROGRESS.md)。

## 1. 当前评价与目标

现版基础可靠，值得继续做，但目前主要是一次性的路径检查工具。已有名称检查、隐含目录冲突、完整性处理及双平台本地验收；主要不足是无法选择交付范围、导出和比较清单、管理历史问题，以及生成更适合 CI 使用的报告。

批准计划的基线估算为手写源码约 1,967 个物理行，其中产品实现约 825 行，其余包含测试和工程脚本；该估算不代替本轮统一口径的代码量统计。需要修复的交付问题包括验收版本与 CI 状态写死，以及工具链下载地址依赖 `latest`。

本轮验收目标：

- 产品源码加有效测试超过 3,000 行，预计约 3,200–4,000 行。
- 排除空行、纯注释、文档、配置、工程脚本、生成文件、依赖和展开的测试数据；分别列出 MoonBit、Node 和测试的统计结果。
- MoonBit 继续承担规则、匹配、比较、基线和报告逻辑，Node 负责文件系统与进程适配。
- 完成 16 个有独立验收结果的提交里程碑，逐次推送、逐次检查 CI。

十月申报应如实说明已有 v0.1 基础及本轮新增能力，不改写真实开发日期。计划沿用现行赛事关于公开持续提交和当期实质新增的要求，月初复核 [官方公告](https://moonbitlang.github.io/Hackathon2026/)。

## 2. 五组功能与接口

### A. 可解释诊断与规则查询

新增 `rules`、`explain CODE`，展示规则原因、反例和整改建议。

详细诊断增加原始路径、条目类型、出现次数和冲突来源。例如文件 `artifact` 与 `artifact/report.txt` 冲突时，两条触发输入都能看见。每组最多展示 5 个来源样例，同时保留完整的冲突成员、计数和截断标记，供机器比较使用。

保留原有 `PathEntry`、`Report`、`parse_manifest`、`audit` 和渲染接口的 v1 行为；新增 `AuditOptions`、`DetailedReport`、`audit_with_options`。CLI v0.2 的审计 JSON 明确升级为 schema 2，并提供迁移说明。

### B. 显式配置与交付范围

```text
moonportcheck scan ROOT --config .moonportcheck.json
moonportcheck check paths.json --exclude "**/*.tmp"
```

配置采用版本化 JSON，首版只提供排除模式；配置与重复的 `--exclude` 参数取并集。默认不排除任何内容，不自动读取 `.gitignore`。

匹配规则由 MoonBit 实现并固定语义：

- 匹配整个相对路径，区分大小写。
- `*`、`?` 不跨 `/`；`?` 匹配一个 Unicode 字符。
- 完整路径段 `**` 匹配零个或多个段；尾部 `/` 表示目录子树。
- 不支持取反、字符类、花括号等扩展；无效模式、未知配置字段退出 `2`。
- 排除目录同时排除其后代，包括清单中的隐含目录；scan/check 结果一致。
- 结构非法路径先保留诊断，不能通过排除规则悄悄隐藏。

报告明确记录有效范围、已排除条目和实际剪枝目录，不推算未遍历子树的文件数量。

### C. 清单导出与比较

```text
moonportcheck snapshot ROOT
moonportcheck diff BEFORE.json AFTER.json --format text
```

`Snapshot` 保存排序后的路径、类型、范围、完整性和扫描问题，不保存内容、时间戳或机器绝对路径。`check` 同时接受原数组清单和新快照；原 `parse_manifest` 接口仍只解析数组。

快照中的路径必须唯一；数组清单仍允许重复并产生规则诊断。检查快照时继承其范围，额外排除只能缩小范围；不完整快照始终保持不完整。

`SnapshotDiff` 比较新增、移除、类型变化及大小写拼写变化。先按原始路径匹配，再对剩余条目进行 ASCII 折叠；只有一对一且类型相同才标记大小写变化，不推测一般重命名或内容变化。两份快照范围不同则退出 `2`。

完整快照导出退出 `0`，不完整退出 `3`；diff 无变化退出 `0`，有变化退出 `1`。

### D. 历史问题基线与增量检查

```text
moonportcheck baseline create REPORT.json
moonportcheck scan ROOT --baseline baseline.json --fail-on new
```

基线只允许从完整的 schema 2 审计报告创建，绑定规则版本与有效检查范围。

诊断组分为 `new`、`existing`、`worsened`、`resolved`：

- 使用“规则编号＋稳定路径锚点”关联同一组；完整成员与次数单独比较。
- 新增成员或任一成员次数上升为 `worsened`。
- 同组减少部分问题仍为 `existing`，整组消失才为 `resolved`。
- `--fail-on new` 对 `new` 和 `worsened` 返回 `1`；默认仍按全部问题判定。
- 基线不匹配退出 `2`；扫描失败始终退出 `3`，不能被基线豁免。

### E. CI 报告与可安装交付

`scan/check` 支持 text、JSON、Markdown、SARIF；diff 支持 text、JSON、Markdown；snapshot 和 baseline 创建固定输出各自的 JSON 文档。

SARIF 使用 2.1.0，正确编码路径，不虚构源码行号；结构非法路径保留为消息和属性，不制造错误的导航位置。先提供 Actions artifact 和步骤摘要，不把格式校验成功等同于 GitHub Code Scanning 接收成功。参考 [GitHub SARIF 支持说明](https://docs.github.com/en/code-security/reference/code-scanning/sarif-files/sarif-support)。

同时修复交付基础：

- 官方下载地址改用完整版本 `0.10.14%2B7d59c7ec9`，保持现有 SHA 校验；两系统使用全新目录进行冷安装验证，失败时不回退 `latest`。
- 验收版本统一读取项目元数据，记录实际执行环境、提交 SHA、Actions run URL。
- 增加公共接口漂移检查、旧版消费者测试，以及包含 LICENSE、说明和校验和的 CLI 压缩包。
- 常规 CI 证据保留 30 天，最终候选验收证据保留 90 天。

## 3. GitHub 工作流与 16 次提交

目标为公开仓库 `AlexenderSokolov/moonportcheck`。计划阶段记录账号已核实、同名仓库尚不存在；执行前必须再次检查，不能覆盖后来出现的仓库。

第 1 次提交如实保存现有 v0.1，并建立 `main`。随后建立 `codex/october-v0.2` 和一个持续 Draft PR；第 2–16 次提交均进入该 PR。

每次固定执行：**实现及对应测试 → 本地检查 → 审查差异 → commit → 立即 push → 核对该 SHA 的 Windows/Linux CI → 下一里程碑。**

| 次数 | 提交成果 | 当次必须通过的验证 |
| --- | --- | --- |
| 01 | 保存真实 v0.1 基线，建立公开仓库 | 原有验收；明确实际开发日期和发布状态 |
| 02 | 固定版本下载、验收元数据、接口与统计门禁 | 双系统冷安装、错误哈希拒绝、版本一致性 |
| 03 | 规则目录及 `rules/explain` | 所有规则可查询，未知编号正确失败 |
| 04 | 详细诊断、来源证据、schema 2 | 隐含目录可追溯、稳定分组、旧 API 不变 |
| 05 | 纯 MoonBit 路径匹配器 | `*`、`?`、`**`、Unicode 和无效模式 |
| 06 | 配置、排除规则及扫描剪枝 | scan/check 范围一致，排除计数可信 |
| 07 | Snapshot 模型、解析和序列化 | 往返一致、排序稳定、损坏输入拒绝 |
| 08 | `snapshot` 命令及 check 快照支持 | 真实目录导出，不完整状态不会丢失 |

| 11 | Baseline 模型及分类核心 | 稳定身份、新成员、重复次数增加 |
| 12 | 基线创建与增量 CI 判定 | 旧问题可见，新问题及恶化失败 |

每项提交同步包含必要的测试和使用说明，不将测试统一拖到最后。

首次基线 CI 若暴露已知工具链问题，下一步只推进修复；后续 CI 失败同样先修复，再增加功能。修复产生额外提交，允许超过 16 次。公开历史不倒拆、不改日期、不 force-push；最终独立审查通过后使用 merge commit 保留全部提交，不 squash。

CI 由主分支 push 和 PR 更新触发，避免一次开发分支推送重复运行两套流水线。最终合并后再核验主分支结果。

## 4. 验收标准

- **兼容性：** 原 v1 库消费者继续通过；新旧公共接口分别验证。新增报告有明确 schema，原有退出码语义保留。
- **组合正确性：** 排除隐含目录、过滤不完整快照、基线成员增加、重复次数上升、范围变化及不同输出格式都有针对性测试。
- **确定性：** 输入重排、配置模式重排不改变语义结果；JS 与 wasm-gc 的新旧报告分别逐字节比对。
- **规模：** 保留十万条正常与冲突输入，增加深层路径、长共同前缀和大型单组冲突；记录耗时、峰值内存和报告体积，不预先承诺性能数字。
- **真实可用：** Windows/Linux 公开 CI、冷工具链安装、独立库消费、CLI 压缩包解包运行均通过。
- **代码量：** 第 10 次提交进行中期统计，第 15 次建立超过 3,000 行的最终门禁。不足时补齐真实行为和覆盖缺口，禁止通过拆行、重复数据或无意义测试充数。
- **过程证据：** 每个里程碑保留 SHA、CI 链接和验证结果；最终报告包含基线至候选版的新增功能与代码量变化。
